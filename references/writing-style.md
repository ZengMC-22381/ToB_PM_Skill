# 写作风格约束（writing-style）

本文件用于约束 `prd-writer-b2b` Skill 的默认输出文风，使其更贴近 ToB / 中后台 / 偏研发对齐的 PRD 写法。

## 1. 总体风格

输出应满足以下要求：
- 专业、克制、结构化
- 偏研发对齐，而不是偏方案销售或偏咨询报告
- 以“可继续编辑、可进入评审、可交付研发”为第一目标
- 不追求花哨表达，不写情绪化修饰
- 默认采用中文输出，术语保持一致

## 2. 结构偏好

默认严格沿用以下主结构：
1. 版本信息
2. 需求背景
3. Roadmap
4. 需求详情
5. 待确认项（如有）

除非用户明确要求，否则不要擅自改成：
- 大段散文式方案说明
- 咨询报告式章节
- 纯页面清单式写法

## 3. 表达方式偏好

### 3.1 多用结构化表达
优先顺序：
1. 表格
2. 分级标题
3. 分点说明
4. Mermaid 流程图（适合时）

### 3.2 少用空泛结论
以下表达只有在后面补足具体解释时才能使用：
- 提升效率
- 优化体验
- 增强能力
- 提升管理效果
- 降低沟通成本

正确写法示例：
- 使企业管理员可在单页内完成审批模板新增、版本发布与停用，减少跨页面配置带来的误操作。
- 将角色授权从“逐人配置”调整为“角色批量授权”，减少高频权限变更时的重复配置成本。

### 3.3 句子长度
- 单句尽量控制在 30 字以内
- 一段尽量只表达一个核心意思
- 当规则较多时，拆成列表而不是写成长段落

## 4. 需求详情的默认写法

在“需求详情”中，默认按“功能模块”组织，每个模块优先包含以下内容：
- 模块名称
- 模块目标
- 功能说明
- 交互说明
- 业务规则
- 边界与异常说明
- 流程原型图 / 流程说明

若某模块不涉及复杂交互，也不应省略“交互说明”，而应写明：
- 无独立交互变化
- 复用现有交互
- 仅新增字段 / 状态 / 按钮

## 5. Roadmap 的默认写法

Roadmap 不只列模块名，必须同时说明：
- 模块说明
- 优先级
- 优先级原因

优先级定义统一使用：
- P0：本期必须完成
- P1：本期建议完成
- P2：后续迭代

优先级原因应尽量落到：
- 主链路闭环
- 前置依赖
- 风险控制
- 兼容性需求
- 增强项属性

## 6. Mermaid 的使用规则

默认不是所有 PRD 都强制输出 Mermaid。
仅在以下情况建议使用：
- 有明显流程流转
- 有审批链路 / 配置链路 / 权限判断链路
- 用文字很难清楚表达步骤关系

不建议为了“看起来完整”而生造复杂流程图。
若信息不足，可写文本流程。

## 7. 参考资料的使用方式

当用户提供参考 PRD、历史方案、会议纪要时：
- 先用于理解现状
- 再用于判断影响范围
- 最后用于支撑新 PRD 写作

必须遵守：
- 参考资料不是最终交付内容
- 新 PRD 必须独立成文
- 不把参考 PRD 与新 PRD 混写
- 不大段复制参考资料原文

## 8. 默认详细度

默认输出详细度为“中高”。
应达到：
- 研发可以理解模块职责
- 设计可以理解主要交互意图
- 评审时可以讨论边界与取舍

但不要默认扩展到：
- 技术实现细节过深
- 数据库字段级设计
- 接口协议级设计
除非用户明确要求。

## 9. 待确认项规则

默认保留“待确认项”。
适用于以下情况：
- 用户输入不完整
- 参考资料版本不一致
- 业务规则存在冲突
- 兼容策略未明确
- 边界是否纳入本期尚未确定

待确认项要具体，不要写成“还有一些细节待补充”。
应写成：
- 历史审批记录是否需要适配新模板版本，待确认。
- 超级管理员是否默认拥有所有数据权限，待确认。

## 10. 示例风格对齐

本 Skill 在写作时，优先对齐以下示例的风格：
- `examples/label-management-prd.md`
- `examples/approval-workflow-config-prd.md`
- `examples/role-permission-management-prd.md`

若示例与用户明确要求冲突，以用户要求为准。
