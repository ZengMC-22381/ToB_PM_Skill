# 写作风格约束（writing-style）

本文件用于约束 `prd-writer-b2b` Skill 的默认输出文风，使其更贴近 ToB / 中后台产品经理的常用 PRD 写法。

## 1. 总体风格

输出应满足以下要求：
- 专业、克制、结构化
- 以产品视角为主，而不是研发实现视角
- 以“可评审、可协作、可继续编辑”为第一目标
- 默认采用中文输出，术语前后一致
- 最终统一以 `.md` 文件交付

## 2. 结构偏好

默认沿用以下主结构：
1. 版本信息
2. 需求背景
3. Roadmap
4. 需求详情
5. 待确认项（如有）

注意：
- 主结构保持稳定
- 局部内容不要被拆成过多二级、三级标题
- 能用一段连贯文字说清楚的，不要强行拆成一串小标题

## 3. 表达方式偏好

### 3.1 以产品语言表达
默认描述应聚焦：
- 谁来用
- 在什么场景下使用
- 系统支持什么能力
- 规则何时生效
- 遇到异常如何处理

避免默认写成：
- 请求体支持传入 labels
- 新增字段 xxx_type
- 表 A 与表 B 建立关联
- 接口返回状态码

更推荐写法：
- 支持管理员为文档配置多个标签，并在文档列表中查看已绑定结果。
- 支持按角色批量分配菜单访问权限，减少逐个成员配置的重复操作。
- 审批模板发布后，仅对新发起的申请生效，已在途流程保持原有规则不变。

### 3.2 多用结构化表达，但不碎片化
优先顺序：
1. 表格
2. 少量分级标题
3. 分点说明
4. Mermaid（适合时）

原则：
- 结构清楚，但不要把文档切得太碎
- 每个功能模块优先写成完整说明，再按需要补列表

### 3.3 少用空泛结论
以下表达只有在后面补足具体解释时才能使用：
- 提升效率
- 优化体验
- 增强能力
- 提升管理效果
- 降低沟通成本

### 3.4 句子长度
- 单句尽量控制在 35 字以内
- 一段尽量只表达一个核心意思
- 规则较多时可拆成列表，但不要为了整齐而机械切标题

## 4. 需求背景的默认写法

“需求背景”不要求拆成“需求来源 / 当前问题 / 目标 / 判断 / 思路”等一串小标题。
更推荐写法是：
- 用几段连续内容讲清楚现状、问题、目标和方向
- 需要强调时，再通过少量加粗或列表补充

## 5. 需求详情的默认写法

在“需求详情”中，默认按“功能模块”组织。
每个模块通常应覆盖：
- 模块目标
- 功能设计
- 使用方式 / 交互方式
- 规则与边界
- 必要时的流程说明

但这些内容不要求全部成为独立小标题。
推荐先写成一段完整设计说明，再在必要处补充：
- 关键规则
- 边界场景
- 流程说明

## 6. Roadmap 的默认写法

Roadmap 不只列模块名，还应说明：
- 模块说明
- 优先级
- 优先级原因

优先级统一使用：
- P0：本期必须完成
- P1：本期建议完成
- P2：后续迭代

## 7. Mermaid 的使用规则

默认不是所有 PRD 都强制输出 Mermaid。
仅在以下情况建议使用：
- 有明显流程流转
- 有审批链路 / 配置链路 / 权限判断链路
- 用文字很难清楚表达步骤关系

## 8. 参考资料的使用方式

当用户提供参考 PRD、历史方案、会议纪要时：
- 先用于理解现状
- 再用于判断影响范围
- 最后用于支撑新 PRD 写作

必须遵守：
- 参考资料不是最终交付内容
- 新 PRD 必须独立成文
- 不把参考 PRD 与新 PRD 混写
- 不大段复制参考资料原文

## 9. 默认详细度

默认输出详细度为“中高”。
应达到：
- 产品、设计、研发都能理解同一份文档
- 可以围绕规则、边界、优先级进行评审

但不要默认扩展到：
- 接口协议级设计
- 数据库字段级设计
- 技术方案评审文档深度

## 10. 交付方式

最终交付物统一使用 `.md` 文件。
不要把完整 PRD 正文直接输出到答案中。
答案中只简要说明：
- 已生成的文件名
- 文件用途
- 是否还有待确认项

## 11. 示例风格对齐

本 Skill 在写作时，优先对齐以下示例的风格：
- `examples/label-management-prd.md`
- `examples/approval-workflow-config-prd.md`
- `examples/role-permission-management-prd.md`

若示例与用户明确要求冲突，以用户要求为准。
