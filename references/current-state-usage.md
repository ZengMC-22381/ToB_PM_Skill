# 现状业务逻辑读取模块使用说明

本文件说明如何使用 `prd-writer-b2b` Skill 的“先读取现状，再撰写新 PRD”能力。

这个模块适合以下真实工作场景：
- 已有旧 PRD，现在要写增量需求
- 已有流程说明，现在要做局部改造
- 已有多个历史文档，现在要统一现状后再起新稿
- 担心新需求误伤旧逻辑，需要先看影响范围

---

## 1. 这个模块解决什么问题

普通 PRD 生成很容易出现两个问题：
1. 把新需求当成从零设计，忽略现有系统逻辑
2. 直接把历史 PRD 拼进新 PRD，导致文档边界混乱

这个模块的作用是：
- 先抽取现有业务逻辑
- 再识别本次需求的改动点
- 最终输出一份独立的新 PRD

注意：
**参考 PRD 只用于参考，不能和最终新 PRD 混写。**

---

## 2. 推荐的使用模式

### 模式 A：内部理解后直接出新 PRD
适合你已经很清楚要什么，只想让 Skill 吃掉旧文档后直接成稿。

推荐输入：

```markdown
请使用 prd-writer-b2b Skill。

基于我提供的参考 PRD 和现有流程说明，先理解当前业务逻辑，再输出一份独立的新 PRD。

注意：
- 参考资料仅用于理解现状
- 新 PRD 必须独立成文
- 不要把参考 PRD 与新 PRD 混写

【参考资料】
- 现有 PRD：
- 现有流程说明：
- 历史角色/权限说明：

【新增需求】
- 需求主题：
- 需求背景：
- 目标：
- 本期范围：
- 约束：
```
```

输出特点：
- 不展示中间分析过程
- 直接输出最终 PRD
- 若信息不足，在 PRD 文末补“待确认项”

---

### 模式 B：先出“现状业务逻辑摘要”，再出新 PRD
适合你对现状还不完全放心，想先检查 Skill 是否理解对了再成稿。

推荐输入：

```markdown
请使用 prd-writer-b2b Skill。

先基于参考 PRD 输出一份《现状业务逻辑摘要》，
确认现状后，再输出一份独立的新 PRD。

注意：
- 参考 PRD 只用于参考
- 《现状业务逻辑摘要》与最终新 PRD 必须分开输出
- 最终 PRD 必须独立成文

【参考资料】
- 现有 PRD：
- 流程说明：
- 现有规则说明：

【新增需求】
- 需求主题：
- 本次改动点：
- 不改动范围：
```
```

输出特点：
- 先出中间摘要
- 再出正式 PRD
- 更适合复杂系统与多文档场景

---

### 模式 C：只做现状梳理，不立即写新 PRD
适合需求还在分析期，先把旧系统吃透。

推荐输入：

```markdown
请使用 prd-writer-b2b Skill。

先不要写新 PRD。
请只根据我提供的参考资料，输出一份《现状业务逻辑摘要》，
重点说明当前核心模块、角色、流程、规则、边界、痛点，以及本次潜在受影响范围。

【参考资料】
- 现有 PRD：
- 流程说明：
- 历史补充资料：

【本次拟做方向】
- 需求主题：
- 初步想法：
```
```

输出特点：
- 只产出中间分析结果
- 不会过早起草方案
- 适合需求澄清会前使用

---

## 3. 最推荐你提供的输入

当你希望 Skill 真正理解现状，建议至少提供这几类信息：

### A. 现有资料
- 现有 PRD
- 历史版本变更说明
- 现有流程说明
- 现有页面或原型说明
- 角色 / 权限规则说明

### B. 本次需求信息
- 需求主题
- 为什么做
- 想改什么
- 哪些不改
- 本期约束

### C. 你对输出过程的要求
- 是否先看现状摘要
- 是否直接出独立新 PRD
- 是否需要把新旧差异写清楚

---

## 4. 模块的内部工作流程

这个模块建议按以下顺序运行：

### Step 1：读参考资料
优先识别：
- 当前系统目标
- 角色
- 业务对象 / 实体
- 主流程
- 规则
- 边界

### Step 2：形成《现状业务逻辑摘要》
推荐参考：
- `references/current-state-summary-template.md`

### Step 3：识别本次改动点
至少说明：
- 新增什么
- 修改什么
- 替换什么
- 兼容什么
- 明确不改什么

### Step 4：识别受影响范围
至少关注：
- 模块影响
- 流程影响
- 权限影响
- 实体影响
- 历史数据兼容

### Step 5：独立输出新 PRD
最终 PRD 必须独立成文，不能把现状摘要和旧文档正文直接拼进去。

---

## 5. 输出边界规则

### 必须做的事
- 可以引用“当前业务逻辑说明”
- 可以写“与现状关系”
- 可以写“改动点”
- 可以写“兼容策略 / 替换策略 / 灰度策略”

### 不能做的事
- 不能把参考 PRD 原文和新 PRD 混在一起
- 不能整段复制旧 PRD 作为新 PRD 的正文
- 不能把旧需求状态当作绝对最新事实而不注明来源
- 不能因为旧文档很长就忽略其核心规则

---

## 6. 推荐的最终输出结构

若采用“先摘要再成稿”的模式，建议输出分为两段：

### 第一段：现状业务逻辑摘要
使用 `current-state-summary-template.md` 的结构，重点写：
- 当前系统目标
- 核心角色
- 核心实体
- 当前模块
- 主流程
- 关键规则
- 受影响范围
- 待确认项

### 第二段：独立的新 PRD
严格使用 `references/prd-template.md` 的结构。
新 PRD 中若要引用现状，只能摘要化写入“需求背景”或“需求详情”的承接说明中。

---

## 7. 典型示例

### 示例 1：基于旧审批流写新版本管理能力
输入意图：
- 已有审批流配置 PRD
- 现在新增“模板版本管理”能力

推荐方式：
- 先输出当前审批模板、节点、发布规则、停用规则的现状摘要
- 再独立输出新 PRD
- 在新 PRD 中说明：新增版本草稿、版本发布、版本回滚、历史实例兼容策略

### 示例 2：基于旧权限系统增加数据权限
输入意图：
- 已有角色权限 PRD
- 现在新增“按部门维度控制数据可见范围”

推荐方式：
- 先识别当前角色授权与菜单权限逻辑
- 再独立输出新 PRD
- 在新 PRD 中说明：本次是在原权限点模型上增加数据范围维度，不重写整个权限体系

## 8. 你在实际使用时最推荐的调用话术

### 快速版
```markdown
请使用 prd-writer-b2b Skill。
基于我提供的参考 PRD，先理解现状业务逻辑，再独立输出一份新 PRD。
注意不要把参考 PRD 和新 PRD 混写。
```

### 稳妥版
```markdown
请使用 prd-writer-b2b Skill。
先根据参考资料输出《现状业务逻辑摘要》，再输出独立的新 PRD。
参考资料仅用于参考，最终 PRD 必须独立成文。
```

### 分析版
```markdown
请使用 prd-writer-b2b Skill。
先不要写新 PRD。
请只整理当前系统的核心模块、角色、流程、规则、边界与受影响范围。
```
