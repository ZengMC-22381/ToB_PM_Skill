# 现有业务逻辑读取与增量写作指南

本文件用于指导 `prd-writer-b2b` Skill 在用户提供已有 PRD、历史方案、流程说明、会议纪要时，先理解现状业务逻辑，再进行增量需求撰写。

## 适用场景
- 用户提供现有 PRD，希望在现有系统基础上新增功能
- 用户提供历史模块说明，希望做优化迭代
- 用户提供多个业务文档，希望 Skill 先统一理解系统现状
- 用户明确要求“结合现有业务逻辑写新需求”

## 核心原则
1. **现有 PRD 是现状的优先信息源**
   - 不要忽略用户给的历史资料，先把它们当作系统当前状态的依据。
2. **先抽取现状，再写增量**
   - 不要一上来直接写新方案，先判断当前系统已有能力、边界、实体、流程、规则。
3. **写“变化点”而不是重写全世界**
   - 新需求优先描述相对现状新增了什么、修改了什么、废弃了什么。
4. **对不确定信息保留待确认项**
   - 若历史文档之间有冲突，不能强行融合成确定事实。

## 建议工作流

### Step 1：读取并总结现状
当用户提供现有 PRD / 业务文档时，先输出或内部整理一份“现状业务逻辑摘要”，至少包括：
- 当前系统目标
- 核心用户角色
- 核心业务对象 / 实体
- 主流程
- 关键业务规则
- 当前模块边界
- 已知限制 / 痛点
- 与新需求直接相关的部分

### Step 2：识别与新需求的关系
明确新需求属于哪一类：
- 新增模块
- 扩展现有模块
- 替换旧逻辑
- 局部优化
- 权限 / 流程 / 配置规则调整

### Step 3：列出“受影响范围”
在写新 PRD 前，先识别：
- 会影响哪些现有模块
- 是否影响已有流程
- 是否影响实体关系
- 是否需要兼容历史数据
- 是否影响已有权限与角色

### Step 4：按增量方式写 PRD
在最终 PRD 中，优先体现：
- 现状是什么
- 本次改动点是什么
- 为什么要改
- 改动后与旧逻辑如何共存或替换
- 是否需要迁移 / 兼容 / 回滚

## 建议补充到输入中的字段
当用户希望 Skill 结合现有业务逻辑写新 PRD 时，优先收集：
- 现有 PRD / 历史方案文档
- 当前系统流程说明
- 现有角色与权限说明
- 现有实体 / 数据结构说明
- 本次新增需求描述
- 本次明确不改动的范围

- 核心角色：
- 主流程：
- 关键规则：
- 当前痛点：

### 本次需求受影响范围
- 受影响模块：
- 新增逻辑：
- 修改逻辑：

## 最终 PRD 的写法建议
在不改变用户既定目录的前提下，建议这样融入现状信息：

### 需求背景中增加
- 当前业务逻辑说明
- 本次改动原因
- 本次改动与现状的关系

### Roadmap 中增加
- 新增模块
- 需改造模块
- 兼容性处理项

### 需求详情中增加
- 现有逻辑承接说明
- 新旧逻辑差异
- 对历史数据 / 历史流程 / 历史角色的影响

## 典型注意事项
1. 不要把历史 PRD 中的旧状态当成绝对最新事实，若用户未确认版本，应标注“基于提供资料判断”。
2. 如果历史文档明显残缺，先抽取可确认部分，再把关键缺口列入待确认项。
3. 若新需求会影响旧流程，必须写清是“并存”“替换”还是“灰度迁移”。
4. 若新需求依赖旧实体结构，应在 E-R 图或模块说明中体现增量变化。

## 参考 PRD 与新 PRD 的边界规则
1. 参考 PRD 的职责是帮助理解当前业务逻辑，不是最终交付正文。
2. 最终交付的新 PRD 必须独立成文，不能把参考 PRD 和新 PRD 合并成一个混合文档。
3. 如果需要体现现状，应写成摘要化内容，例如“当前业务逻辑说明”“与现状的关系”“改动点说明”，不能直接拼接原始参考 PRD 大段内容。
4. 如果用户给了多份旧资料且版本不一致，先做现状摘要，再把冲突点列入待确认项。
5. 若用户要求先看分析过程，建议先按 `current-state-summary-template.md` 输出中间摘要，再单独输出新 PRD。
